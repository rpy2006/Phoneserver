2. IMPLEMENTATION SUMMARY
================================================================================
An incremental upgrade that turns PhoneServer into a local-first SQL database
and file-storage platform, without removing or rewriting existing features.

Added:
  * Projects — isolated containers for databases, files and backups, with a
    stable generated id used as the on-disk identifier.
  * SQL database management — create/list/delete per-project SQLite databases;
    schema/table/index inspection; parameterised queries; transactions;
    export/import; a SQL workspace UI. Guarded by SqlGuard and bounded by row
    limits and a time budget.
  * Persistent file storage — streamed uploads with SHA-256 checksums, MIME
    detection, folders, rename/move/delete, per-project quotas and per-file
    limits, range downloads, orphan/missing-file detection.
  * Backups — full project backups (databases + stored files + safe config),
    validation, download, restore and import, with retention (max 25).
  * HTTP API — a versioned JSON API under /api/v1 for apps and websites.
  * API tokens — SHA-256 hashed, project-scoped, read-only capable.
  * UI — project list/detail, SQL workspace, file browser, backups, API token
    management, and an in-app API documentation screen, wired into the
    existing Home/Advanced-Settings navigation.
  * Tests — JUnit + Robolectric suites for the storage layer and the HTTP API.
  * Documentation — web/API.md plus web/ (architecture, storage, security,
    testing, platform compatibility).

All data lives outside build directories under a configurable data root; file
contents are stored on the filesystem and only metadata is stored in SQL.

Also added a project-local debug keystore and signing config so every build
(AndroidIDE, PC, any HOME) signs with the same key and can update the installed
app in place, avoiding INSTALL_FAILED_UPDATE_INCOMPATIBLE.

7. DATABASE INITIALIZATION
================================================================================
Nothing manual is required. On first use:

  1. The app creates the data root if it does not exist (app-private external
     dir by default; see §13 for the configurable override).
  2. system.db is created there under system/ with its schema (projects,
     project_databases, files, folders, api_tokens, backups, operations) and a
     schema version. Upgrades are applied additively via onUpgrade.
  3. Each project database is a separate SQLite file created under
     <root>/projects/<project-id>/databases/<name>.db on demand.

To create the first project and database see §10.

8. BUILD / RUN
================================================================================
Build:
  sh gradlew :app:assembleDebug

Run tests:
  sh gradlew :app:testDebugUnitTest

Run:
  Install/run the debug APK on an Android device, start the server from the
  app's home screen (Start Server). The HTTP server listens on port 8080.
  The API base URL is http://<device-ip>:8080/api/v1.
  Verify with:  curl http://<device-ip>:8080/api/v1/health

Requires JDK 21 and an Android SDK configured in local.properties
(sdk.dir=<path>). local.properties is machine-specific and is NOT in this
archive.

10. INSTALLATION / INTEGRATION
================================================================================
1. Extract Phoneserver-SQL-Storage-Update.zip into the root of an existing
   PhoneServer checkout. The archive preserves original relative paths and
   contains no nested project directory, so files overwrite/add in place.
2. Confirm local.properties points at a valid Android SDK.
3. Build: sh gradlew :app:assembleDebug

Creating the first project and database (in the app):
  * Open Projects → "New project" → enter a name.
  * Open the project → Databases → "New database" → enter a name.
  * Open the database to create tables via the SQL workspace.

In the app you can also switch the SQL workspace and file browser between your
projects, and open API docs from Settings.

================================================================================
11. BACKUP / RESTORE
================================================================================
  * Create: project → Backups → "Create backup" (include files optional).
    Backups are stored in <root>/projects/<id>/backups/ and keep at most 25
    (oldest pruned).
  * Download/Export: from the backups screen or
    GET /api/v1/projects/<id>/backups/<backupId>/download.
  * Validate: POST …/backups/<backupId>/validate (checks format/version and
    rejects unsafe archive paths).
  * Restore: POST …/backups/<backupId>/restore {"confirm":true} — replaces the
    project's databases (and files if included) after a fully validated
    extraction; the previous copy is preserved until the swap succeeds.
  * Import: POST …/backups/import?confirm=true with a raw zip body.

A backup includes the project's databases, stored files and a safe-to-export
project-config.json. It NEVER includes the access password, API tokens or
other secrets.

================================================================================
12. KNOWN LIMITATIONS
================================================================================
  * No TLS in the app. HTTP is plaintext; for any non-LAN access put it behind
    an HTTPS reverse proxy or VPN. See web/security.md.
  * No encryption at rest; data is stored unencrypted in the app-private data
    root (device encryption aside).
  * SQLite is single-file/single-node: do NOT share a database file over a
    network filesystem or treat it as a distributed database.
  * Robolectric DB tests cannot run on Linux/aarch64 hosts (see §9).
  * Instrumentation tests were not run (no emulator/device available).
  * Default rate limit, quotas and size caps are configurable but conservative;
    tune per deployment.
  * Debug signing key changed: an app previously installed and signed with a
    different debug key must be uninstalled once before this build can be
    installed (Android forbids replacing an app signed with a different key:
    INSTALL_FAILED_UPDATE_INCOMPATIBLE). After that, app/debug.keystore keeps
    signatures stable so updates apply in place. The debug keystore is not a
    secret but should be replaced with a private release key for distribution.

Explicit non-goals / production requirements are detailed in web/security.md.

================================================================================
13. REQUIRED CONFIGURATION CHANGES
================================================================================
  * Access password: set one in the app so /api/v1 admin access uses a password
    (if unset, only API tokens work; anonymous admin is refused).
  * Data root (optional): Advanced Settings → data root. Defaults to an
    app-private persistent directory; no change needed for typical use.
  * CORS origins (optional): the existing allowed-origins setting is honoured
    by the API (default "*"). Set a comma-separated list to restrict it; leave
    empty to disable CORS headers entirely.
  * API rate limit (optional): api_rate_limit_per_minute (default 240,
    minimum 10).
  * local.properties: must contain sdk.dir=<Android SDK path>. Not included in
    the archive.
  * Debug signing: app/build.gradle now uses app/debug.keystore for debug
    builds. No configuration is required; keep the keystore in the project and
    do not delete it, or debug signatures will change again. For a distributable
    release build, add your own release signingConfig and keep the private key
    out of version control.
