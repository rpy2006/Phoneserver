01 — Setup

From APK to first clientfive steps

Work through these once, in order. Steps 3 and 5 are the ones people skip and regret: an unauthenticated server on a shared Wi-Fi is open read/write access to the phone's shared storage, including recursive delete.

Step 01 · Install

Install the APK

Android 7.0+ (minSdk 24), arm64-v8a only. Build with ./gradlew assembleDebug or install the release APK signed with your own key — the debug keystore is project-local so AndroidIDE, a PC, and CI all update the same install.

app/build/outputs/apk/

Step 02 · Permissions

Grant what the server needs

All files access so uploads land in the real Pictures/, Movies/, Music/ and Download/ folders; Notifications on Android 13+ for the ongoing service notification; and Start on Boot if the server should survive a reboot.

Settings → Permissions

Step 03 · Authenticate

Set the access password

Settings → Security → Authentication. The username is optional; the password protects /files, the file APIs and remote browsing. Leave both blank and the row says so plainly: “No password set — open access on your Wi-Fi.”

Do this before the first client connects

Step 04 · Start

Start the local server

Home → Local Server card → Start. A foreground service keeps the socket alive with an ongoing notification that shows the live address, and the launcher icon swaps to the online artwork while it runs.

Quick action: “Start Server” on Home

Step 05 · Connect

Reach it from a client

On the same Wi-Fi, open http://<phone-ip>:8080 in any browser or curl. GET /status is public — use it as the reachability ping. Everything else answers with a 401 challenge until credentials are supplied.

Or use the QR tab to onboard another phone

Step 05b · Verify

Prove it end to end

Run the smoke test from a second device: hit /status, list a folder with credentials, upload one file, then confirm the request and byte counters moved on the Dashboard tab. If they did, the path is real.

Full command list in Operations →

02 — Everyday use

The workflows you run daily

The app opens on a five-tab bottom bar — Home, Dashboard, QR, Chat, Settings — and the hamburger in every screen's header opens the side drawer for everything that lives one level deeper.

Drawer · Files

Share and browse files

Upload, download, rename, move and delete from the phone or from a browser. Files open in the built-in viewers for images, video, audio, text and PDF; anything else is handed to the system chooser. Uploads are media-scanned immediately, so Gallery and Music see them without a rescan.

GET /files/<path> · POST /api/upload

Drawer · Remote Servers

Pair other phones

Save a profile (name, host, port, credentials, note) or scan the other phone's QR code to prefill it. Each profile shows a live online/offline dot from the public /status ping, and remote files open in the same built-in viewers.

QR tab → “My QR” / “Scan QR”

Tab · Dashboard

Watch live traffic

Request count, bytes up and down, connected clients parsed by OS and browser, per-endpoint hits, RAM and app CPU, uptime, a 4-second-poll sparkline per metric and a rolling activity feed — the local server plus every saved remote server in one view.

GET /api/stats (password-gated)

Drawer · Website Editor

Host a small website

The served site is files/website/index.html plus the CSS, JS and images next to it, delivered at GET /. The editor manages it as a real file tree: upload several files, create folders, rename, delete, open.

No build step, no deploy target

Drawer · API Endpoints

Define mock endpoints

Map (method, path) → JSON body with custom response headers and documented parameters — a tiny stub server for front-end work. Built-in paths win if they collide.

Custom /api/* routes are public on the LAN — see Hardening

Drawer · Projects & Database

Store data locally

Projects isolate workspaces; each holds many SQLite databases with a guarded SQL workspace (single statements, parameterised queries, row limits, time budget). Files carry SHA-256 checksums, and scoped API tokens are stored only as hashes.

Everything is reachable under /api/v1

04 — Hardening

Treat the LAN as the trust boundary

PhoneServer is deliberately local-first. What separates a demo you start by hand from a service you can leave running is the checklist below — none of it takes more than five minutes.

Set a password before the first client Settings → Security → Authentication must not read “No password set”. With no password the whole shared storage is writable by anyone on the Wi-Fi.
Prefer scoped API tokens for scripts Projects → API tokens issues per-project and/or read-only bearer tokens, stored only as SHA-256 hashes, instead of circulating the shared password.
Tighten CORS Advanced Settings → Allowed CORS origins. Empty means same-origin only, * lets any website call the API, or list exact origins such as https://app.example.com.
Keep the rate limit on Advanced Settings → API rate limit per minute, per client IP, minimum 10. It is the only throttle between a runaway script and the device.
Verify from outside the phone Run /status and one authenticated call from a second device on a different network segment. Localhost success proves nothing about the LAN.
Schedule backups Projects → Backups builds a validated zip (manifest, databases, stored files, metadata.json) that can be re-validated, restored, or imported on another device.
Decide the reboot policy Settings → “Start server on boot” plus the boot receiver. For an unattended device, enable it; for a phone you carry, leave it off and start on demand.
Assume credentials are visible The access password and saved server profiles live in plain SharedPreferences. Treat the device — and anything that restores its backups — as trusted.

Known limits you should plan around

  • Plaintext everywhere. Cleartext HTTP on port 8080 with no TLS; anything on the path can read it.
  • Password in a query string. The client can pass ?pw=, which lands in server logs, browser history and proxy logs. Prefer the X-Auth-Password header or HTTP Basic.
  • Custom endpoints bypass the gate. A user-defined /api/* route is reachable without the password — by design, and a foot-gun if you publish something sensitive.
  • Shared-storage root. The file browser covers the device's shared storage, not a sandbox, so scope your client-side deletes carefully.

Full analysis: Security model in the docs.

05 — Operations

Verify, troubleshoot, recover

Keep this section open on the client machine. Every check below is observable from outside the phone, which is the only vantage point that matters.

smoke-test.sh 
# 1. reachability — no password needed
curl http://<phone-ip>:8080/status

# 2. protected read
curl -u :mypassword \
     "http://<phone-ip>:8080/api/browse?path=Pictures"

# 3. protected stats (header form)
curl -H "X-Auth-Password: mypassword" \
     http://<phone-ip>:8080/api/stats

# 4. write: folder + upload
curl -X POST -H "X-Auth-Password: mypassword" \
     -H "Content-Type: application/json" \
     -d '{"path":"","name":"TestFolder"}' \
     http://<phone-ip>:8080/api/mkdir

curl -X POST -H "X-Auth-Password: mypassword" \
     -F "file=@./photo.jpg" \
     "http://<phone-ip>:8080/api/upload?path=TestFolder"

# 5. confirm the Dashboard counters moved
Illustrative values · replace the address and password
  • Client cannot reach the address Both devices must be on the same Wi-Fi with client isolation/AP isolation off. Use /status from the client as the test — the phone's own loopback always works.
  • 401 on a call you expect to pass Credentials travel as X-Auth-Password: …, ?pw=…, or HTTP Basic — the username is ignored, only the password is compared. If no password is set the gate is removed entirely and every request is authorised.
  • Uploads do not appear in Gallery Grant All files access. Without it the server falls back to the app's private sandbox folder, so files never reach the real Pictures/ tree and no media scan happens.
  • Server stops when the screen locks Keep the foreground service notification; it holds a partial wake lock while serving. If a battery optimiser kills it, exempt the app.
  • Chat reports “AI chat isn't available” The native bridge failed to load, or the import was rejected. Model imports are validated first: vision projectors (mmproj) and truncated files are refused with a readable message.

06 — Developers

Everything is an HTTP endpoint

Browse, mkdir, delete, rename, upload, stats and custom JSON routes on the classic API; projects, databases, files, backups and tokens under /api/v1. A website served from the phone can call the same API the app does.

Open the API reference Testing notes
api-v1.sh 
# liveness — public
curl http://<phone-ip>:8080/status

# list projects with a scoped token
curl -H "Authorization: Bearer pst_..." \
     http://<phone-ip>:8080/api/v1/projects

# parameterised query against a project database
curl -X POST -H "Authorization: Bearer pst_..." \
     -H "Content-Type: application/json" \
     -d '{"sql":"SELECT * FROM notes LIMIT ?","params":[20]}' \
     http://<phone-ip>:8080/api/v1/projects/<pid>/query
Tokens are per-project and optionally read-only
07 — Optional add-on

Run a small ad network from the same phone

Ad Network Manager is off by default. When enabled it listens on a separate 8090 socket with its own database, accounts and dashboard; the file server on 8080, its password and its data are untouched. No cloud account, ad exchange or third-party SDK is involved.

Step 01 · Enable

Turn it on and claim admin

Settings → Ad Network → enable, then start the server. Open http://<phone-ip>:8090 and enter the one-time setup code shown only on the phone to create the first administrator.

Separate opt-in; nothing starts by itself

Step 02 · People

Add a publisher and an advertiser

An admin approves sites and campaigns, manages balances and can review fraud. A publisher registers a domain and placement; an advertiser creates a campaign, uploads a creative and submits it for review. Sign-up is off by default.

Roles: admin · advertiser · publisher

Step 03 · Embed

Paste one tag on the site

Only approved sites with active placements serve. Copy the tag from the placement, keep the page CSP permissive for the ad origin, and test from a real hostname — bare IP addresses are rejected by design.

HTTP on the LAN; HTTPS pages need public_base_url

ad-tag.html 
<!-- placement tag from the dashboard -->
<div data-adnet-placement="pl_0123456789abcdef"></div>
<script async src="http://<phone-ip>:8090/sdk.js"></script>
Viewability = 50% visible for 1 second · no fill returns 204 · no fake ads

Before you expose it

  • Plaintext HTTP. Port 8090 has no TLS. Keep it on a trusted LAN; use a reverse proxy for HTTPS and set public_base_url to that origin.
  • It is not an ad exchange. Fraud checks are heuristics, there is no email verification or CAPTCHA, and billing is a local ledger — settle real money out of band.
  • Back it up separately. adnet.db and filesDir/adnet/creatives/ are not included in /api/v1 project backups.
  • Do not tag this docs site. web/ promises no third-party requests; the ad server is documented, not embedded.
