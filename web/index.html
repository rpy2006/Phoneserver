PhoneServer

Turn any Android phone into a network file server, mini website host, live-traffic monitor, a small on-device AI chat, and an optional self-hosted ad network — all from one APK, with no backend and no internet requirement.

PhoneServer runs a real HTTP server directly on the device (java.net.ServerSocket, no NanoHTTPD, no embedded webview server). Any browser, curl, or another phone on the same Wi‑Fi can reach it at http://<phone-ip>:8080 and browse, upload, download, and organise the phone's shared storage.

1.1 Local HTTP server

Uploads land in the device's real Pictures/, Movies/, Music/, Download/ folders and are pushed to MediaScannerConnection immediately.

1.2 Remote client (phone-to-phone)

  • Save unlimited server profiles
  • Live online/offline dot per profile
  • Browse, upload, download, rename, delete on the remote device
  • QR onboarding

1.3 Live dashboard

Real telemetry: request count, bytes up/down, clients, per-endpoint hit counts, RAM %, CPU %, uptime, sparklines, activity feed.

1.4 Website & API authoring

  • Website editor manages the served site
  • API endpoint editor defines method → JSON mappings

1.5 On-device AI chat

  • Imports a .gguf text model
  • Validates the GGUF header
  • Token-streaming chat UI via native llama.cpp

1.6 Platform integration

  • Foreground service with notification
  • Optional start-on-boot
  • Launcher icon swaps between online/offline
  • DayNight theme support

1.7 Local SQL & file storage platform

  • Projects — isolated workspaces
  • Databases — many SQLite databases per project
  • Files — streamed with SHA-256 checksums
  • Backups — validated zip archives
  • API tokens — scoped, hashed

Everything is reachable over HTTP under /api/v1.

1.8 Optional ad network

An opt-in, self-hosted ad server on a separate port (8090).

4. Architecture Design

4.1 Architectural style

A layered, message-passing-free monolith with three loosely-coupled tiers.

┌──────────────────────────────────────────────┐
│  PRESENTATION TIER                           │
├──────────────────────────────────────────────┤
│  SERVICE / ENGINE TIER                       │
│  ServerService → SimpleHttpServer → Stats    │
├──────────────────────────────────────────────┤
│  STATE / UTILITY TIER                        │
│  ContentStore · ServerProfileStore · …       │
└──────────────────────────────────────────────┘

4.2 Request lifecycle

Browser/curl
    ↓
acceptLoop()  [dedicated thread]
    ↓
handleClient(Socket)
    ├ 1. readRequest()
    ├ 2. CountingOutputStream
    ├ 3. route(req, out)
    └ 4. ServerStats.recordRequest()

8. On-device AI Subsystem

8.1 Component shape

ChatFragment → ModelStore.importModel → LlmEngine.loadModel → generate

8.2 Concurrency correctness

The native unload frees the llama_context, so loadModel must hold the lock for the entire swap.
  1. loadModel() holds generationLock for the entire swap.
  2. generate() reads nativeHandle inside the lock.
  3. nativeUnloadModel wrapped in try/catch.
  4. Callbacks swallow Throwable.

8.3 GGUF validation

Rejects non-GGUF magic, truncated headers, version outside 2–3, and vision projectors.

8.4 UI robustness

  • viewAlive flag
  • pendingTokens buffer
  • Coalesced flush Runnable
  • 20,000-char cap

9. Security Model

9.1 Posture

  • usesCleartextTraffic="true"
  • Plain HTTP on 8080 / 8090
  • No password = open LAN access

9.2 Controls

  • Canonical-path containment
  • Name injection rejection
  • Multipart filename stripping
  • User-supplied headers filtered
  • All Activities exported="false"

9.3 Weaknesses

  • Plaintext credentials at rest
  • Password in URL query
  • Plaintext compare
  • Custom endpoints public
  • Traversal guard bypass on filenames

11. Design Decisions

11.1 Hand-rolled HTTP server

Dependency would be a supply-chain and size cost.

11.2 Byte-safe parsing

Reader would corrupt binary upload bodies.

11.3 Counting output

Bytes served is a headline number.

11.4 Connection: close

Removes keep-alive timeout handling.

11.5 Single chokepoint

One function to audit.

11.6 Graceful degradation

Crashes on missing grant are unusable.

11.7 Background threads

Consistent with strict-mode.

11.8 Descriptive names

Maintained by reading.

11.9 Icon aliases

Only supported way to change launcher icon.

Data & storage API (/api/v1)

The local SQL + file storage platform is exposed as a versioned JSON API.

  • Base URL: http://<device-ip>:8080/api/v1
  • Content type: application/json; charset=utf-8
  • Errors: {"error":"<message>","status":<code>}

1. Authentication

Every endpoint requires authentication except GET /health and OPTIONS.

1.1 Access password

  • Header — X-Auth-Password: my-secret
  • Query — ?pw=my-secret
  • Basic — Authorization: Basic base64(user:my-secret)

1.2 API token

Authorization: Bearer pst_3f9c…

Tokens can be global or project-scoped, read-write or read-only. Only the SHA-256 hash is stored.

1.3 Failure responses

  • 401 — Missing/invalid credential
  • 403 — Valid but not allowed
  • 429 — Rate limit exceeded

1.4 Rate limiting

Default 240/min per client IP.

1.5 CORS

Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE, OPTIONS
Access-Control-Allow-Headers: Authorization, Content-Type, X-Auth-Password
Access-Control-Max-Age: 600

5. Notes on the SQL workspace

  • One statement per request.
  • Values via params; the guard blocks dangerous constructs.
  • Row results paginated and time-bounded.
  • Local-first store, not a hardened multi-tenant SQL service.

Architecture

This document describes the local SQL + file storage platform that was added on top of PhoneServer.

Component map

SimpleHttpServer (8080)
    ↓
DataApi (auth, rate limit, CORS, JSON framing)
    ↓
ProjectStore · DatabaseManager · FileStore · BackupManager · TokenStore
    ↓
system.db + filesystem

Layers

  1. Transport — SimpleHttpServer
  2. API facade — DataApi
  3. Stores — data/ package

Request lifecycle

  1. Parse request
  2. If /api/v1 → DataApi.handle()
  3. Reject too-large buffered bodies → 413
  4. OPTIONS → CORS preflight
  5. GET /health → public
  6. Rate limit then authenticate
  7. Route to handler
  8. Store + render JSON

Design choices

  • Metadata in SQL, content on disk
  • Generated ids and keys
  • Parameterised SQL + static guard
  • Defence in depth for paths
  • One connection style
  • Safe error messages

Threading

SimpleHttpServer handles each connection on its own thread.

Storage layout

All persistent platform data lives under a single configurable data root.

Where the data root lives

  1. Advanced Settings → data_root
  2. App-private external directory
  3. App-private internal directory

Directory structure

<root>/
  system/system.db
  tmp/
  projects/<project-id>/
    databases/<name>.db
    files/<storage-key>
    backups/<backup-id>.zip
    project-config.json

system.db schema

TablePurpose
projectsProject records
project_databasesRegistered databases
filesStored-file metadata
foldersLogical folders
api_tokensAPI credentials
backupsBackup archives
operationsRolling log

Project databases

Each logical database is an independent SQLite file with foreign keys, WAL and busy_timeout=5000.

Uploads and temporaries

Streamed into tmp/<prefix>-<id>.part then renamed into files/<storage-key> after full write + SHA-256.

Security model

Security review for the local SQL + file storage platform.

Threat model

  1. No unauthenticated admin surface
  2. No cross-project data access
  3. No filesystem escape
  4. No SQL escape
  5. No secret leakage
  6. Bounded resource use

Authentication

  • Access password (admin, constant-time)
  • Bearer token (pst_…, scoped, hashed)
  • Anonymous admin refused if no password

Authorisation

requireProjectAccess rejects project-scoped tokens on other projects.

Path safety

  • normalizeRelative rejects .., ., empty
  • sanitizeFileName strips reserved chars
  • safeResolve canonicalises both root and candidate

SQL safety

  • One statement per request
  • Blocked: ATTACH, DETACH, load_extension, writable_schema
  • Explicit transactions rejected
  • Parameterised only

Uploads & downloads

  • Limits against declared and streamed bytes
  • Multipart buffered + capped
  • Range downloads
  • Attachment unless inline-safe

Backups

  • Validated format/version/safe paths
  • Root-checked, size-capped extraction
  • Restore/import only after validated extraction

Resource limits

  • Per-IP rate limit
  • Buffered bodies capped
  • Row + time budget

Error handling

DataException carries safe client messages.

CORS

Origins from ContentStore.getAllowedOrigins (default *).

Non-goals

  • No TLS in the app
  • Bearer secrets
  • No audit-grade logging
  • No encryption at rest
  • No protection against malicious local apps
