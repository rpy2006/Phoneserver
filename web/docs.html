PhoneServer

Turn any Android phone into a network file server, mini website host, live-traffic monitor, a small on-device AI chat, and an optional self-hosted ad network — all from one APK, with no backend and no internet requirement.

PhoneServer runs a real HTTP server directly on the device (java.net.ServerSocket, no NanoHTTPD, no embedded webview server). Any browser, curl, or another phone on the same Wi‑Fi can reach it at http://<phone-ip>:8080 and browse, upload, download, and organise the phone's shared storage. The same APK can also act as a client — connecting to other phones running PhoneServer and browsing them remotely. An opt-in Ad Network Manager can run alongside it on port 8090, with its own database, accounts and dashboard.

New to the app? The Production Guide is the operator tutorial — install, set a password, start the server, pair a client, harden the LAN boundary and verify each change. This site is the reference: architecture, HTTP API, storage, security and testing.

Uploads land in the device's real Pictures/, Movies/, Music/, Download/ folders and are pushed to MediaScannerConnection immediately, so Gallery, Music and Video apps see them without a rescan.

1.2 Remote client (phone-to-phone)

  • Save unlimited server profiles (name, host, port, credentials, note)
  • Live online/offline dot per profile via the public /status ping
  • Browse, upload, download, rename, delete on the remote device
  • Open remote files in the built-in viewers, or hand off to any installed app via FileProvider
  • QR onboarding: show your server as a QR code, scan another phone's QR code to prefill a new profile

1.3 Live dashboard

Real (never simulated) telemetry: request count, bytes up/down, connected clients with parsed OS/browser, per-endpoint hit counts, RAM %, app-process CPU %, uptime, a 4-second-poll sparkline per metric, and a rolling recent-activity feed. Aggregates the local server plus every saved remote server into one view.

1.4 Website & API authoring

  • Website editor manages the served site as a real file tree — upload multiple files, create folders, rename, delete, open
  • API endpoint editor lets you define (method, path) → JSON body mappings with custom response headers and documented (informational) parameters — a tiny mock-server builder

1.5 On-device AI chat

  • Imports a .gguf text model into private app storage
  • Validates the GGUF header before loading (rejects vision projectors / mmproj files with a human-readable message)
  • Token-streaming chat UI via a native llama.cpp bridge
  • Partial-import protection (.part file + verified rename) and free-space preflight checks

1.6 Platform integration

  • Foreground service with an ongoing notification showing the live address
  • Optional start-on-boot receiver
  • Launcher icon swaps between online/offline artwork by toggling two activity-alias components
  • DayNight theme support; a distinct light "Home" theme

1.7 Local SQL & file storage platform

A local-first storage layer that turns the phone into a small database + object-storage backend for other apps, websites, and scripts — still with no cloud dependency.

  • Projects — isolated workspaces, each with a generated ASCII-safe id used as its directory name
  • Databases — many SQLite databases per project, created/queried/inspected from the UI or the HTTP API, with a guarded SQL workspace (single statements, parameterised queries, row limits, time budget)
  • Files — streamed upload/download (range-capable) with per-file SHA-256 checksums, folders, rename/move, MIME detection, quota and per-file size limits
  • Backups — validated zip archives (manifest + databases + stored files + metadata.json) that can be downloaded, re-validated and restored, or imported from another device
  • API tokens — scoped (per-project and/or read-only) bearer tokens, stored only as SHA-256 hashes
  • Storage insights — real per-project database/file/folder counts, byte sizes, free space and a rolling operation log

Everything in this layer is reachable over HTTP under /api/v1 (see API.md) and through new screens in the app (Projects, Project detail, SQL workspace, Files, Backups, API tokens, API docs). See architecture.md, storage.md, security.md and testing.md in this folder for architecture, storage layout, security and testing notes.

1.8 Optional ad network

An opt-in, self-hosted ad server on a separate port (8090), database (adnet.db), file store and account system. Publishers register a domain and placement and copy a small tag; advertisers manage campaigns, creatives, budgets and targeting; admins approve sites/campaigns, manage users, credit/pay balances, review fraud and export reports. It is fully offline and never shares authentication or data with the file server.

  • Public delivery: /sdk.js, /serve, /imp, /c, /media/<id>; management API under /api/*
  • Real, server-signed impression/click tokens; viewability ≥50% for 1 s; no fake ads or simulated numbers
  • Internal admin / advertiser / publisher accounts, PBKDF2 passwords and 12-hour bearer sessions
  • CPM/CPC billing in integer micros with a configurable publisher revenue share (default 70%)
  • Strict-CSP dashboard with sites, placements, campaigns, creatives, reports, users, billing and fraud review

See Ad Network Manager and ad-network.md for setup, the embed contract, targeting, fraud rules, retention and the full API.

4. Architecture Design

4.1 Architectural style

A layered, message-passing-free monolith with three loosely-coupled tiers. There is no DI container, no repository abstraction over the filesystem, and no ORM — the codebase deliberately optimises for readability over cleverness, which the core server file states explicitly:

"One thread per connection. Simple on purpose — this runs on a phone, not a data-center box, and simple code is far easier to keep working than clever code."

4.3 The "measured twice" design

This is the most distinctive architectural decision in the codebase. Every number the dashboard shows is a real measurement. There are two independent paths that converge on identical UI:

  LOCAL                                  REMOTE
  ─────                                  ──────
  Socket request                         RemoteApiClient.getStats()
      ↓                                       ↓
  CountingOutputStream                    HTTP GET /api/stats
  (counts actual bytes written)                ↓
      ↓                                   JSON body
  ServerStats.recordRequest()                  ↓
  (AtomicLong accumulators,             StatsSnapshot DTO
   ConcurrentHashMap per path,                  ↓
   ClientInfo per IP)              ┌───────────┴───────────┐
      ↓                            │                       │
  /api/stats builds JSON      DashboardFragment     DashboardActivity
      │                       (fragment, live)     (legacy, unregistered)
      └──────────────┬────────────────────────────┘
                     ▼
           ServerStats.get()  or  StatsSnapshot
                     ▼
           SparklineView / TrafficChartView

CountingOutputStream is the key to "no fake numbers" — it is a thin OutputStream decorator that increments a counter on every write, and it is the only way bytes leave a response. There is no estimate, no File.length() approximation.

Two classes document deliberately honest limits rather than fabricating data:

  • DeviceStats.getAppCpuPercent() reports this app process's CPU (Process.getElapsedCpuTime() delta over wall-clock, normalised by core count), not device-wide CPU, because Android 8+ blocks system-wide CPU reads without root. The Javadoc says so explicitly.
  • ServerStats.parseUserAgent() is a substring match, described as "very lightweight... just enough to show a friendly OS/browser guess."

4.4 Threading model

There is no ExecutorService, coroutines, AsyncTask, or ViewModel in the UI layer. The convention is:

new Thread(() -> { /* blocking work */ handler.post(() -> { /* touch views */ }); })
                    ↑ always a named Thread for server/LLM work, for logcat attribution
Component Thread strategy Rationale
Socket accept 1 dedicated long-lived thread Single accept loop, trivially correct
Per-connection 1 thread per connection, try (Socket s = ...) Simplicity; closes the socket on exit
HTTP client (remote) new Thread() per call All blocking I/O, documented "must be called from a background thread"
LLM token generation Single-thread ExecutorService + ReentrantLock Serialises generation; the lock is a correctness requirement, not a style choice (see §8.2)
LLM callbacks Handler(Looper.getMainLooper()) Tokens delivered on the main thread
UI polling Handler.postDelayed self-reposting runnable 2 s (Home), 3 s (QR), 4 s (Dashboard); removed in onPause

Known cost of this model: no cancellation on lifecycle change and no bound on concurrent threads. DashboardActivity.pollRemote and ServersListActivity spawn one thread per server per poll tick, and RemoteBrowseActivity keeps uploading into a dead destination after a rotation. This is listed in §12.

4.5 Storage layout

ContentStore is the single source of truth for every path. It degrades gracefully when "all files access" is not granted:

Purpose With MANAGE_EXTERNAL_STORAGE Without it (fallback)
Served website — (always private) filesDir/website/
Shared files root (/files, /api/browse, uploads) Environment.getExternalStorageDirectory() — i.e. the whole device, same view Gallery sees getExternalFilesDir("public")
Downloaded remote files Download/PhoneServer/ getExternalFilesDir("downloads")
Model files — (always private) filesDir/models/
View cache (for FileProvider handoff) — (always private) cacheDir/view_cache/

4.6 Path-traversal defence

ContentStore.resolveSafePathUnder(root, relative) is the one chokepoint:

  1. Strip leading /
  2. Empty → return root itself
  3. new File(root, relativePath)
  4. Compare getCanonicalPath() of target against getCanonicalPath() of root
  5. Must be equal to root, or start with root + File.separator — otherwise null

Canonicalisation (not string prefix matching) means .. segments, symlinks and // collapsing are all resolved before the check, so ../../etc/passwd is rejected.

Handlers additionally apply name-level validation before touching the filesystem: - handleMkdir / handleRename reject names that are empty, contain /, or contain .. - MultipartParser.extractFilename strips any directory component the browser may have sent, keeping only the last path segment - writeResponse strips Content-Length and Connection from user-defined headers so a custom endpoint cannot corrupt response framing

Known gap: the guard is bypassed when a filename (rather than a path) is appended after resolution — see §12.

4.7 Auth model

  isAuthorized(request)
        │
        ├─ stored password empty?  ──────────────▶ ALWAYS TRUE (open LAN access)
        │
        ├─ header "X-Auth-Password" matches? ────▶ authorised
        ├─ query param "pw" matches? ────────────▶ authorised
        └─ "Authorization: Basic base64(user:pass)"
                 └─ base64-decode, split on first ':'
                      └─ password half matches? ─▶ authorised
                                             else ─▶ 401 + WWW-Authenticate: Basic

Three credential channels exist so that (a) browsers get a native Basic-Auth prompt, (b) curl can use a header, and (c) the app's own RemoteApiClient can use a header while download() additionally appends ?pw= for clients that cannot set headers. Comparison is plaintext String.equals.

4.8 Response framing

writeResponse builds headers by hand and always sets:

HTTP/1.1 <code> <reason>
Content-Type: <type>
Content-Length: <exact byte count>
Connection: close
Access-Control-Allow-Origin: *
[user-defined headers, minus content-length/connection]

Connection: close on every response means one request per TCP connection — the correct trade-off for a phone server, and it removes keep-alive timeout management entirely. Content-Length is computed from the byte array length, never from a String.length(), which matters because guessMime returns UTF-8 content and non-ASCII file bytes would otherwise be miscounted.

4.9 Icon switching

A launcher icon cannot be swapped at runtime, so the manifest declares two activity-alias components pointing at the same MainActivity, differing only in android:icon:

                android:icon="@drawable/ps_online"  android:enabled="false" />

8.2 Concurrency correctness (this is the subtle part)

LlmEngine guards all native lifecycle operations with one ReentrantLock, and the Javadoc explains exactly why:

"The native unload frees the llama_context and model, so running it while a generation is still decoding from that context reads freed memory and segfaults. loadModel used to take only the instance monitor, which generate() never took, so a re-import from the AI tab could free the context underneath a running answer."

Consequences, all deliberate and commented in-code:

  1. loadModel() holds generationLock for the entire swap (unload + load), not just the load.
  2. generate() reads nativeHandle inside the lock and copies it to a local final — checking modelLoaded up front and using the field later left a use-after-free window.
  3. nativeUnloadModel is wrapped in try/catch (Throwable) because an abort there kills the process with no log line at all.
  4. All three callback dispatchers (deliverToken/deliverComplete/deliverError) swallow Throwable, because a token stream outlives the view that started it and an exception from a destroyed fragment would otherwise take down the whole process — including the file server.

8.3 GGUF validation

ModelStore.GgufInfo is a ~120-line RandomAccessFile reader that parses only the header key/value block — no tensor is touched, so it costs a few KB of reads even on a 600 MB file. It defends against:

  • Non-GGUF magic → isGenuineGguf = false
  • Truncated header → BadHeaderException on implausible lengths (string > 4096 B, kvCount > 4096, negative counts, array count > 10 M, value nesting depth > 4)
  • Version outside 2–3
  • Vision projectors. This is the notable one:

"The 600 MB file in Download/Office Kit is named smollm2-135m-instruct-q8_0.gguf but its header says it is an mmproj — a CLIP vision projector for a Qwen3-VL multimodal model, with no text decoder. Handing that to the inference engine produced an opaque failure that looked like the app dying, so it is now rejected up front by name."

Detection: general.type == "mmproj" or general.architecture == "clip" → rejected with a message naming the model and asking for the matching language-model .gguf.

8.4 UI robustness

ChatFragment treats "a view may vanish mid-generation" as the normal case:

  • A viewAlive flag plus nulled references in onDestroyView; every view touch re-checks
  • pendingTokens buffer collects tokens while no view is attached and flushes when the view returns
  • Tokens are coalesced onto one pending Runnable rather than one Handler.post per token — per-token setText + relayout was stalling long enough for the system to reclaim the process
  • finishGeneration() drains the buffer before appending the trailing newline, since the last tokens may still be buffered
  • history is capped at 20,000 chars and persisted via onSaveInstanceState; trimming triggers a full setText rather than an append
  • Auto-load and import run on named threads (chat-model-autoload, chat-model-import) so a crash is attributable in logcat — an uncaught throwable on a bare Thread goes to the default handler and kills the process, taking the file-server UI with it
  • getActivity() null checks are re-done inside postToUi, because it can go null between the check and runOnUiThread on a worker thread

9. Security Model

9.1 Posture

PhoneServer is a local-network service. It is not hardened for the public internet, and it does not pretend to be:

  • usesCleartextTraffic="true" + network_security_config.xml with cleartextTrafficPermitted="true"
  • File-server traffic is plain HTTP on port 8080; when enabled, the ad server is plain HTTP on port 8090
  • Default posture with no password set is unauthenticated LAN-wide read/write access to the device's shared storage, including recursive delete. The Settings UI says so explicitly: "No password set - open access on your Wi-Fi"
  • MANAGE_EXTERNAL_STORAGE is requested, which is a very high-privilege grant

11. Design Decisions & Rationale

The codebase is unusually explicit about why it is built the way it is — most non-obvious decisions carry a Javadoc paragraph explaining the failure they replaced. The most important ones:

11.1 Hand-rolled HTTP server instead of NanoHTTPD

Decision: 671 lines of ServerSocket + InputStream + hand-built response headers, zero server dependencies. Why: the server is the product. A dependency would be a supply-chain and size cost for something the app fully controls; the file is self-documenting and easy to repair. The router is a flat if/else chain precisely so it is auditable at a glance.

11.2 Byte-safe request parsing

Decision: readLine reads byte-by-byte with an explicit ISO-8859-1 decode, and the body is read by Content-Length via readExactly. Why: reading the stream through a Reader would corrupt binary upload bodies. The ISO-8859-1 decode is byte-preserving by definition, so no information is lost in the request line or headers.

11.3 Counting output rather than estimating traffic

Decision: CountingOutputStream wraps the socket's OutputStream; handleClient feeds the counter to ServerStats. Why: "bytes served" is a headline dashboard number. Measuring the actual socket writes is the only way it can be honest. The same discipline appears in DeviceStats, which refuses to report a device CPU figure it cannot legitimately obtain.

11.4 Connection: close on every response

Decision: always close, never keep-alive. Why: removes keep-alive timeout handling, socket-pool state, and half-open connection bugs from a thread-per-connection model. On a phone with a handful of LAN clients, the handshake cost is irrelevant.

11.5 A single traversal chokepoint

Decision: every served path resolves through ContentStore.resolveSafePath / resolveSafeWebsitePath. Why: one function to audit is worth more than twenty call sites each doing their own substring checks. Canonical-path comparison (not string prefix) closes .. and symlink escapes in one step.

11.6 Graceful degradation over failure

Decision: getPublicFilesDir() falls back to a private sandbox when MANAGE_EXTERNAL_STORAGE is not granted; LlmEngine reports unavailability instead of throwing when the .so fails to load; IconSwitcher swallows everything. Why: an Android app that crashes on a missing optional grant is unusable. Every optional capability degrades to a clearly-labelled reduced mode.

11.7 Background work on background threads, always

Decision: every blocking call — HTTP, file copy, GGUF parse, model load — runs off the main thread; the reversed mistakes are noted as bugs in comments (main-thread file copies in WebsiteFilesActivity, main-thread read/write in WebsiteEditorActivity). Why: consistent with Android's strict-mode model, and it makes the main-thread violations obvious against the norm.

11.8 Descriptive names, and comments that explain history

Decision: no abbreviations (acceptLoop, resolveSafePathUnder, CountingOutputStream, pendingTokens); comments explain what broke and why the code is shaped this way, not what the line does. Why: this is a codebase maintained by reading it. ContentStore, SimpleHttpServer, LlmEngine, ModelStore, ChatFragment and DeviceStats are effectively annotated design documents.

11.9 Two activity-aliases for a live status icon

Decision: declare two launcher entries and flip their enabled state. Why: it is the only supported way to change a launcher icon at runtime on Android. The enabled attribute, not the icon, is the switch.

12.5 Scalability limits (inherent to the design)

  • Whole files are read fully into a byte[] before being written (readFile, SimpleHttpServer.handleUpload, RemoteApiClient.upload) — a 2 GB upload will OOM. There is no streaming to disk.
  • The entire request body is buffered in memory (Request.body) — Content-Length is trusted with no cap, so a malicious or buggy client can declare a huge body.
  • HomeFragment.countFilesRecursive is depth-capped at 4 and runs on every 2 s refresh tick.
  • TrafficChartView uses raw pixel padding (90 px left, 40 px bottom) rather than dp, so axis labels collide on high-density screens, and its colours are hardcoded hex rather than resolved from R.color.* — invisible to dark mode.
  • SparklineView initialises max = Float.MIN_VALUE, which is the smallest positive float, not the most negative. It happens to work only because every current input is a non-negative percentage.

13. Extension Guide

13.1 Add a new HTTP endpoint

  1. Add a constant to SimpleHttpServer, alongside the existing path literals: java private static final String PATH_API_SEARCH = "/api/search";
  2. If it touches files, add it to the password-gate condition in route(): java if (path.equals("/api/browse") || ... || path.equals(PATH_API_SEARCH)) { if (!isAuthorized(req)) { writeUnauthorized(out); return; } }
  3. Write the handler, mirroring handleMkdir: - Resolve any client-supplied path via ContentStore.resolveSafePath(appContext, relative) - Return null → 404, unsafe path → 400 - Build the response with writeResponse(out, code, "application/json", body)
  4. Extend the client if the app itself should use it: add a method to RemoteApiClient following the getJson / postJson pattern (8 s connect, 15 s read, X-Auth-Password header, 401 → ApiException("Wrong password")).
  5. Update the route table in §5 of this README.

13.2 Add a new tab

  1. Create XFragment extends Fragment with onCreateView / onViewCreated.
  2. Add a layout in res/layout/fragment_x.xml and a res/menu-independent icon in res/drawable/ic_x.xml.
  3. Add PAGE_X and a case to MainPagerAdapter; bump getItemCount().
  4. Add the nav item to res/menu/bottom_nav_menu.xml.
  5. Add the mapping in both MainActivity.pageToNavId and navIdToPage.
  6. Bump setOffscreenPageLimit(4) if you have more than 5 tabs.

13.3 Add a new file viewer

  1. Add the extensions to the relevant case in FileTypeUtils.classify.
  2. Create XViewerActivity with public static final String EXTRA_PATH = "path".
  3. Register it in AndroidManifest.xml with android:exported="false".
  4. Add a case to both openFile methods (FilesActivity and WebsiteFilesActivity), and to RemoteBrowseActivity's equivalent.

13.4 Add a persisted collection

  1. Create a <Name>Store with a private SharedPreferences file name and a KEY_LIST = "..._json".
  2. getAll — parse defensively, return an empty list on any parse failure (never throw).
  3. getById / find — linear scan; these collections are small by design.
  4. save — assign a UUID.randomUUID() id if absent, else replace by id.

Data & storage API (/api/v1)

The local SQL + file storage platform is exposed as a versioned JSON API. This document is the complete reference. It is self-contained; the in-app ApiDocsActivity screen shows a short summary.

  • Base URL: http://<device-ip>:8080/api/v1
  • Content type: requests and responses are application/json; charset=utf-8 unless a binary resource is streamed.
  • Errors: {"error":"<message>","status":<code>} with a meaningful HTTP status code.
  • Port: fixed at 8080 (ServerService.PORT).

1. Authentication

Every endpoint under /api/v1 requires authentication except GET /health (public liveness probe) and OPTIONS (CORS preflight).

Two credential kinds are accepted:

1.1 Access password (admin)

Grants admin rights to all projects. Supply it in any one of these ways:

Method Example
Header X-Auth-Password: my-secret
Query parameter ?pw=my-secret
HTTP Basic Authorization: Basic base64(user:my-secret) (only the password part is checked)

If no password is configured on the device, anonymous admin access is refused — you must use a token.

1.2 API token (scoped)

Authorization: Bearer pst_3f9c…

Tokens are created in the app (or via POST /tokens by an admin). They can be:

  • global (access every project) or project-scoped (one project only);
  • read-write or read-only.

Only the SHA-256 hash of a token is stored; the plaintext (pst_ + 64 hex characters) is returned once at creation and cannot be shown again. Revoking a token takes effect immediately.

A project-scoped admin request cannot create projects. A read-only credential is refused on every mutating route (including SQL write statements).

1.3 Failure responses

Status Meaning
401 Unauthorized Missing/invalid credential. Adds WWW-Authenticate: Basic realm="PhoneServer"
403 Forbidden Valid credential but not allowed (wrong project, read-only, non-admin)
429 Too Many Requests Per-IP rate limit exceeded (Retry-After: 60)

1.4 Rate limiting

Requests are limited per client IP using the configured api_rate_limit_per_minute (default 240/min; minimum 10). Exceeding it returns 429.

1.5 CORS

The allowed origins come from the app's allowed_origins setting (default *). If set to a comma-separated list, only matching Origin headers receive Access-Control-Allow-Origin. An empty value disables CORS headers entirely.

Preflight (OPTIONS) returns 204 with:

Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE, OPTIONS
Access-Control-Allow-Headers: Authorization, Content-Type, X-Auth-Password
Access-Control-Max-Age: 600

Credentials are never advertised via Access-Control-Allow-Credentials.

2.6.1 POST …/{db}/query

{"sql":"SELECT * FROM notes WHERE id = ?","params":[1],"limit":100,"offset":0,"timeBudgetMs":5000}
  • sql (required): a single statement. SELECT/WITH/EXPLAIN/PRAGMA are read-only; INSERT/UPDATE/DELETE/REPLACE/CREATE/DROP/ALTER are writes and need a read-write credential.
  • params (optional): bound values, referenced with ? (or :name/@name/ $name). Never interpolate.
  • limit (default 100, max 1000), offset (default 0), timeBudgetMs (default 5000, max 30000; exceeded → 408).

Result (read):

{"isSelect":true,"keyword":"select","rowsAffected":0,"truncated":false,
 "durationMs":1,"columns":["id","body"],"rows":[[1,"hello"]],"rowCount":1}

Result (write):

{"isSelect":false,"keyword":"insert","rowsAffected":1,"truncated":false,"durationMs":0}

Binary SQL values are returned as base64:<data>. A result that hits the row limit sets "truncated": true.

2.6.2 POST …/{db}/transaction

{"statements":[
  {"sql":"INSERT INTO notes(body) VALUES(?)","params":["a"]},
  {"sql":"UPDATE notes SET body=? WHERE id=?","params":["b",1]}
]}

Plain strings are also accepted as elements. All statements run in one transaction; on any error the transaction is rolled back. Response is a query result with the summed rowsAffected. Explicit BEGIN/COMMIT/ROLLBACK/SAVEPOINT are rejected — this endpoint is the transaction mechanism.

2.6.3 Export / import

  • export streams a consistent copy of the database (Content-Type: application/vnd.sqlite3), using VACUUM INTO where supported.
  • import replaces the database. It requires ?confirm=true and a raw SQLite body. The uploaded bytes are verified with PRAGMA integrity_check and the previous file is preserved under backups/ as <name>.db.pre-import-<timestamp> before the swap. Invalid/empty files are rejected (400).

2.7.1 Upload

Two forms are supported.

Raw body (recommended; streamed, for large files):

curl -X POST "http://<ip>:8080/api/v1/projects/<pid>/files?folder=albums&name=photo.jpg&description=beach&tags=holiday" \
     -H "Authorization: Bearer pst_…" \
     -H "Content-Type: image/jpeg" \
     --data-binary @photo.jpg

Content-Length is required (otherwise 411); the body is streamed off the socket. The MIME type comes from the request Content-Type.

multipart/form-data (buffered, capped):

curl -X POST "http://<ip>:8080/api/v1/projects/<pid>/files" \
     -H "Authorization: Bearer pst_…" \
     -F "file=@photo.jpg"

Query parameters folder, name, description, tags are optional. The stored file name is sanitised; the original name is kept in metadata. A SHA-256 checksum is computed while streaming.

Limits: per-file upload limit (project override or 512 MiB default) and per-project storage quota both return 413; the file-count limit returns 409. Both the declared length and the streamed byte count are checked.

2.7.2 Download

  • Streamed from disk with Content-Length, Accept-Ranges: bytes, and support for Range: bytes=… (206 Partial Content; 416 if unsatisfiable).
  • Served as attachment by default. Add ?inline=1 (or ?inline=true) to request inline rendering; this is honoured only when the MIME type is on the small inline-safe allow-list (images, plain text, audio, mp4/webm, PDF).

5. Notes on the SQL workspace

  • One statement per request. Use the transaction endpoint for multi-step work.
  • Values must be passed via params; string building is not needed and the guard blocks dangerous constructs (ATTACH, DETACH, load_extension, writable_schema, selected PRAGMAs, explicit transactions).
  • Row results are paginated (limit/offset) and time-bounded.
  • This is a local-first store, not a hardened multi-tenant SQL service. See web/security.md for the full threat model and production requirements (notably: put it behind HTTPS/VPN for any non-LAN access).

Architecture

This document describes the local SQL + file storage platform that was added on top of PhoneServer. It complements the high-level overview in the project README and the request-level reference in API.md.

The platform is deliberately small: a thin data/ storage layer, a single HTTP facade (DataApi), and a set of Android screens that drive the same layer. Nothing depends on a cloud service, an account, or an external database server.

Layers

  1. Transport — SimpleHttpServer. The existing single-file HTTP server. It was extended to (a) recognise /api/v1 paths, (b) leave large raw (non-multipart) upload bodies on the socket so DataApi can stream them, (c) cap buffered (multipart / small) bodies, and (d) hand the request to DataApi.handle(...). It also adds the CORS response header using the configured origins.

  2. API facade — DataApi. A stateless dispatcher that turns HTTP requests into storage-layer calls and back into JSON. It owns authentication, per-project authorisation checks, rate limiting, CORS preflight, JSON parsing/rendering, and streaming of downloads and exports. It never touches SQLite directly — it always goes through the store classes.

  3. Stores — the data/ package. Each store owns one concern and is the only place that reads/writes the corresponding tables/files:

Store Responsibility
SystemDatabase Declares/creates system.db and its schema; provides the singleton helper
ProjectStore Project lifecycle, per-project/global statistics, operation log
DatabaseManager Per-project SQLite databases: create/list/delete, schema inspection, guarded query execution, transactions, export/import
FileStore Streamed uploads, folders, download metadata, rename/move/delete, usage, integrity checks
BackupManager Create/validate/download/restore/import project backups, retention
TokenStore Issue/verify/revoke/list API tokens (hash-only persistence)
  1. Persistence. system.db holds metadata only. Database files and stored file bytes live on the filesystem under a single configurable data root (see storage.md). User-supplied names are never used as paths.

Request lifecycle for /api/v1

  1. SimpleHttpServer parses the request line, headers and (depending on the route) either buffers or defers the body.
  2. If the path is under /api/v1 it calls DataApi.handle(context, req, out).
  3. DataApi rejects explicitly-too-large buffered bodies with 413.
  4. OPTIONS is answered as a CORS preflight before authentication.
  5. GET /api/v1/health is answered publicly.
  6. Otherwise the per-IP rate limit is enforced (429 when exceeded), then the caller is authenticated.
  7. The first path segment selects a handler (system, tokens, projects); project-scoped handlers verify the caller may touch that project.
  8. The handler calls the relevant store and renders JSON (or streams bytes). DataException carries the intended HTTP status.

Design choices

  • Metadata in SQL, content on disk. Large media is never stored as SQL blobs; only a generated storage key is. This keeps the metadata database small and makes range downloads trivial.
  • Generated ids and keys. Project ids, database ids, file ids and file storage keys are all generated (UUID-derived / random). The id is the directory or file name on disk, so path traversal is structurally impossible rather than merely filtered.
  • Parameterised SQL + a static guard. Ordinary data operations never build SQL from user strings; the SQL workspace additionally runs every statement through SqlGuard (single-statement only, forbidden keywords blocked, read-only enforcement) and applies row limits and a time budget.
  • Defence in depth for paths. PathGuard normalises, validates and then re-checks the canonicalised result is inside the expected root, even though the storage layout already avoids user-controlled path segments.
  • One connection style. Project databases are opened with foreign keys, WAL and a busy timeout. system.db uses WAL and cascading foreign keys so deleting a project removes its metadata rows atomically while on-disk data is removed first (so a failure never silently loses data).
  • Safe error messages. DataException messages are written to be returned to clients; SQLite errors are passed through safeMessage(...), which replaces absolute paths with <path>.

Threading

SimpleHttpServer handles each connection on its own thread. Stores are stateless apart from the SystemDatabase singleton and the cached RateLimiter; SQLite serialises access internally (WAL + busy timeout). The UI performs storage work off the main thread and observes the same layer the API uses, so there is no second source of truth.

Storage layout

All persistent platform data lives under a single configurable data root. Nothing is ever written into build directories, the app's private files root is only used as a fallback, and file contents are kept out of SQL.

Where the data root lives

ContentStore.getDataRoot(context) resolves the root in this order:

  1. The path configured in Advanced Settings (server_config → data_root), if it exists and is writable.
  2. The app-private external directory …/Android/data/<applicationId>/files/phoneserver-data.
  3. The app-private internal directory files/phoneserver-data (fallback when external storage is unavailable).

Points 2 and 3 are app-private: not world-readable, survive app updates, and are removed when the app is uninstalled. Point 1 lets an advanced deployment place data on shared storage.

The root is resolved once per operation via ContentStore.getStorageLayout().

Project databases

Each logical database is an independent SQLite file under projects/<project-id>/databases/. DatabaseManager.openFile enables foreign keys, WAL and PRAGMA busy_timeout = 5000 for writable opens. New files are created with PRAGMA auto_vacuum = INCREMENTAL.

DatabaseManager.list reconciles the metadata table with what is actually on disk and adopts any *.db file it finds without metadata (for example after a manual copy), so nothing becomes invisible.

When a database is deleted its sidecar files (-wal, -shm, -journal) are removed too, so re-creating a database of the same name cannot inherit stale state.

Uploads and temporaries

Uploads are streamed into tmp/<prefix>-<id>.part and renamed into files/<storage-key> only after the bytes are fully written and the SHA-256 checksum computed. On any failure the temp file is deleted. Restores extract into tmp/restore-<id>/ and swap directories into place only after a complete, validated extraction (the previous copy is kept until the swap succeeds).

Security model

This document is the security review for the local SQL + file storage platform. It states what is protected, how, and — importantly — what is not protected so that deployments are not over-trusted.

Threat model

The intended deployment is a phone on a trusted local network, reachable by other devices on that network (or by the phone itself). There is no cloud component and no multi-tenant hardening. The security goals are therefore:

  1. No unauthenticated administrative surface.
  2. No cross-project data access with a project-scoped credential.
  3. No filesystem escape via crafted names, folder paths or archives.
  4. No SQL escape via crafted statements or parameters.
  5. No secret leakage to clients through error messages or responses.
  6. Bounded resource use (request size, rows, time, rate).

Authentication

/api/v1 is authenticated by either:

  • Access password (interactive / admin). Supplied as X-Auth-Password: <pw>, ?pw=<pw>, or HTTP Basic auth. This grants admin rights across all projects. Comparison uses a constant-time equality check (TokenUtil.constantTimeEquals).
  • Bearer API token (Authorization: Bearer pst_…). Tokens are created from the app (or the /tokens endpoint by an admin), can be scoped to a single project and/or marked read-only, and are stored only as SHA-256 hashes. The plaintext is shown exactly once at creation.
  • If no password is configured, anonymous admin access is refused: a token is required. This avoids the "empty password = open admin panel" mistake.

GET /api/v1/health is the only unauthenticated endpoint. OPTIONS (CORS preflight) is answered before auth so browsers can negotiate.

Only an admin (password) credential can call /api/v1/system and /api/v1/tokens. A project-scoped admin request may not create projects.

Authorisation & project isolation

requireProjectAccess rejects a project-scoped token from touching any other project. Combined with the storage layout — every project is a directory named by its generated id, and a token stores only that id — this makes cross-project access structurally impossible, not just filtered by the API layer. A read-only token (canWrite=false) is refused on every mutating route via requireWrite, including the SQL workspace's write statements.

Path safety

PathGuard is used everywhere user input could influence a path:

  • normalizeRelative rejects .., ., empty segments, and separators inside segments.
  • isValidSegment / sanitizeFileName strip or replace reserved characters and never return an empty name.
  • safeResolve / isInside canonicalise both the root and the candidate and verify the result is inside the root.

Because ids/keys are generated and used as the actual on-disk names, these checks are the second line of defence, not the first.

SQL safety

SqlGuard.inspect runs before any statement reaches SQLite:

  • Exactly one statement per request (a top-level ; with more than one non-empty statement is rejected). Splitting is quote/comment aware.
  • Forbidden constructs are blocked: ATTACH, DETACH, load_extension, writable_schema, and several dangerous PRAGMAs (temp_store_directory, data_store_directory, lock_status, database_list).
  • Explicit transaction control (BEGIN/COMMIT/ROLLBACK/SAVEPOINT) is rejected — use the transaction endpoint instead.
  • Only SELECT/WITH/EXPLAIN/PRAGMA (read) and INSERT/UPDATE/DELETE/REPLACE/CREATE/DROP/ALTER (write) are allowed; write verbs are refused on a read-only credential.

The workspace is parameterised: params are bound, never interpolated. Identification names used internally (PRAGMA table_info, VACUUM INTO, row counting) are quoted with " and doubled. Scope/statement analysis is done per database file, and the layer only ever opens a file that is inside the project's own databases/ directory.

This is a local-first data store, not a hardened multi-tenant SQL service. There is no per-statement sandbox beyond the guard and limits above.

Uploads & downloads

  • Upload limits are enforced against both the declared length and the actual streamed byte count (413 on violation).
  • Multipart bodies are buffered and capped; large raw uploads are streamed off the socket so memory is not exhausted.
  • Downloads and exports stream from disk and support Range; 416 is returned for unsatisfiable ranges.
  • Uploaded content is served as an attachment unless the MIME type is on a small allow-list of inline-safe types (MimeTypes.isInlineSafe), so user content cannot execute scripts in the server's origin. Responses also carry X-Content-Type-Options: nosniff and Cache-Control: private, max-age=0.

Backups

  • An archive is a zip with a manifest.properties; validation requires the expected format/version and rejects any entry that is absolute, contains a backslash, or is not a safe relative path.
  • Extraction is root-checked (PathGuard) and capped (4 GiB) to resist archive bombs.
  • Restore/import replace data only after a full validated extraction into a staging directory; the previous copy is preserved until the swap succeeds.
  • Backups contain the project's databases, stored files and safe-to-export project-config.json. They never contain the access password, API tokens, or other secrets.

Resource limits

  • Per-IP rate limit (ContentStore.getApiRateLimitPerMinute, default 240/min) returns 429 with Retry-After: 60.
  • Buffered request bodies are capped (413 above the cap).
  • Query row limits and a time budget bound scans; exceeding the budget returns 408.
  • Row counts, database counts, file counts and backup counts are all bounded.

Error handling

Client-visible messages come from DataException and are written to be safe. SQLite error text is passed through safeMessage, which replaces absolute paths with <path>. Unexpected exceptions return a generic 500 internal server error; details are only logged on-device.

CORS

CORS origins come from ContentStore.getAllowedOrigins (default *). An empty value disables CORS headers entirely (same-origin only). Credentials are never advertised via Access-Control-Allow-Credentials, so browsers will not attach ambient credentials cross-origin.

Explicit non-goals / production requirements

  • No TLS in the app. HTTP is plaintext. For any access beyond a trusted LAN you must put the server behind an HTTPS reverse proxy (or a VPN/SSH tunnel) and terminate TLS there. Anything on the same network can otherwise read credentials and data.
  • The access password and tokens are bearer secrets. Anyone who obtains them has the associated scope. Tokens can be revoked from the app/API.
  • No audit-grade logging or login throttling beyond the per-IP rate limit.
  • No encryption at rest. Files and databases are stored unencrypted in the app-private data root. Device-level encryption is the only protection.
  • No protection against a malicious local app on a rooted/compromised device.

Do not treat this as production security for sensitive or multi-user data.

The Ad Network Manager is an optional, self-hosted advertising server inside PhoneServer. 7. Counting, fraud and billing

  • /serve issues an HMAC-SHA256-signed token: v1|nonce|campaign|creative|placement|site|issued|visitor. Impression tokens live 6 hours; click tokens 24 hours; each token is single-use.
  • Impressions count only after the viewability rule. Clicks require a prior valid impression for the same nonce.
  • Billing uses integer micros: CPM charges bid/1000 per valid impression, CPC charges bid per valid click. The publisher share is rev_share_pct (default 70%).
  • A valid event updates campaign spend and advertiser balance in the same transaction and stores cost_micros/pub_micros.
  • Invalid events are stored with valid=0 and a reason, but are never billed and never earn.

Admins can review flagged sites. The review flags (never auto-bans) a site with a 48-hour CTR above 15% (≥100 impressions) or an invalid-traffic share above 40% (≥50 events).

Privacy: DNT: 1 or Sec-GPC: 1 suppresses the visitor id (no frequency capping/per-visitor fraud check) but does not suppress the ad. The visitor id is a daily-rotating HMAC of IP+UA; no raw IP, no cookie and no cross-day link. Bots and no-fill get 204.

11. Security and privacy

  • Separate surface: port, database, files, thread pool and prefs are independent of the file server; enabling ads cannot weaken file-server auth.
  • Accounts: PBKDF2-HMAC-SHA256 (60,000 iterations, 16-byte salt), 10–128 character passwords with letters and digits, 12-hour bearer sessions stored only as SHA-256 hashes, revocation on logout/password change/disable.
  • First admin: one-time phone-shown setup code; setup is refused after any user exists and is rate-limited.
  • Login abuse: per IP+email and per-IP limits; unknown emails run a dummy hash to equalise timing.
  • Authorisation: admin-only routes checked server-side; publishers/advertisers are scoped to their own records; foreign ids return 404.
  • Delivery: key + approved site + active placement + matching Origin/Referer; HMAC-signed, expiring, single-use tokens; prior impression required for clicks; bots and no-fill get 204.
  • Input/response safety: strict validation, image sniffing, bound SQL parameters, fixed report group expressions, CR/LF stripping, nosniff, no-store on APIs, X-Frame-Options: DENY and strict/sandbox CSPs.
  • Privacy: no cookies, no raw-IP visitor storage, daily-rotating visitor hash, DNT/GPC honoured for visitor tracking, no third-party requests or cloud services.

Residual risks: plaintext HTTP on the LAN, no TLS in the app, no email verification/password reset/CAPTCHA, and heuristic (not perfect) fraud detection. Treat this as a small private ad server, not an ad exchange. For anything beyond a trusted network, terminate TLS at a reverse proxy and keep port 8090 private.
